
# 06. Controllers and Reconciliation

## 1. Почему одного CRD недостаточно?

Представим, что мы создали объект:

```yaml
apiVersion: lab.example.com/v1
kind: Database
metadata:
  name: payments-db
spec:
  engine: postgres
  version: "17"
```

Kubernetes сохранил его.

Но где PostgreSQL?

Его нет.

CRD только расширяет API Kubernetes. Он не выполняет действия на основании spec.

Для этого нужен Controller.

## 2. Что такое Controller?

Controller — компонент, который наблюдает за Kubernetes-ресурсами и приводит фактическое состояние к желаемому.

В нашем случае Controller будет следить за Database.

Упрощённая логика:

1. Получить Database.
2. Прочитать spec.
3. Проверить, существует ли соответствующий StatefulSet.
4. Если отсутствует — создать его.
5. Если конфигурация отличается — обновить его.
6. Обновить status Database.

## 3. Reconciliation Loop

Главный принцип Kubernetes Controllers — reconciliation loop.

Controller постоянно сравнивает:

Desired State — что пользователь хочет получить.

Actual State — что реально существует.

Если состояния отличаются, Controller предпринимает действия.

Пример:

```text
Database CR
    |
    v
Controller
    |
    v
Проверка StatefulSet
    |
    +---- StatefulSet отсутствует
    |          |
    |          v
    |      Создать StatefulSet
    |
    +---- StatefulSet существует
    |          |
    |          v
    |      Проверить конфигурацию
    |
    +---- Конфигурация отличается
               |
               v
           Обновить StatefulSet
```

После выполнения операции Controller снова проверяет состояние.

## 4. Почему Controller должен быть идемпотентным?

Controller может получать одно и то же событие несколько раз.

Поэтому повторная обработка не должна приводить к неправильному состоянию.

Например:

Если StatefulSet уже существует и соответствует Database, Controller не должен создавать его повторно.

Он должен понимать, что желаемое состояние уже достигнуто.

Это называется идемпотентностью.

## 5. Events и Watches

Controller использует механизм наблюдения за Kubernetes API.

Он может получать уведомления об изменениях:

- создан объект;
- обновлён объект;
- удалён объект.

Но важно понимать: события не являются единственным источником истины.

Controller также использует периодические повторные проверки и очередь обработки.

Это помогает восстанавливаться после временных ошибок и пропущенных событий.

## 6. Spec и Status

Controller читает:

```yaml
spec:
  engine: postgres
  version: "17"
```

И может обновлять:

```yaml
status:
  phase: Ready
  message: Database is running
```

Spec — желаемое состояние.

Status — наблюдаемое состояние.

Пользователь изменяет Spec.

Controller сообщает результат в Status.

## 7. OwnerReferences

Если Controller создаёт StatefulSet для Database, часто используется OwnerReference.

Это позволяет связать дочерний объект с родительским.

Например:

Database
  |
  +-- StatefulSet
  +-- Service
  +-- Secret

При корректно настроенном владении Kubernetes Garbage Collector может удалять зависимые объекты при удалении владельца.

Но для этого необходимо учитывать настройки propagation policy и жизненный цикл ресурсов.

## 8. Практическое задание

Пока у нас нет собственного Controller.

Попробуй смоделировать его работу вручную:

1. Создай Database.
2. Посмотри её spec.
3. Создай StatefulSet с соответствующей конфигурацией.
4. Измени version в Database.
5. Сравни желаемое и фактическое состояние.
6. Вручную обнови StatefulSet.

Ты выполнил те же концептуальные действия, которые позже автоматизируем через Controller.

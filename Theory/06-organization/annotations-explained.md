
# Аннотации (Annotations) в Kubernetes

Аннотации — это механизм для хранения **произвольной, неидентифицирующей метаинформации** об объекте. В отличие от меток (Labels), которые используются для поиска и фильтрации через селекторы, аннотации нужны для того, чтобы «прикрепить» к объекту любую служебную информацию, которая нужна инструментам, операторам или людям.

## 🎯 Зачем они нужны? (Главные сценарии)

### 1. Хранение конфигурации для инструментов и операторов
Это самый частый случай в проде. Аннотации читают другие программы (Ingress Controllers, cert-manager, ArgoCD, Prometheus и т.д.), чтобы понять, как им себя вести с этим объектом.
*   *Пример (Nginx Ingress):* `nginx.ingress.kubernetes.io/rewrite-target: /` — говорит Nginx, куда перенаправлять трафик.
*   *Пример (cert-manager):* `cert-manager.io/cluster-issuer: letsencrypt-prod` — говорит cert-manager, что для этого Ingress нужно выпустить сертификат.

### 2. Описание объекта для людей
В отличие от `name`, которое ограничено 63 символами и правилами DNS, в аннотации можно написать целое предложение.
*   *Пример:* `description: "This deployment is owned by the payments team. Contact: payments@company.com"`.

### 3. Указание на «владельца» или источник создания
Инструменты вроде Helm или ArgoCD пишут в аннотации информацию о том, кто создал объект.
*   *Пример (Helm):* `meta.helm.sh/release-name: my-release` — Helm понимает, что этот объект принадлежит его релизу, и его можно удалять при `helm uninstall`.

### 4. Отладочная информация
*   *Пример:* `kubectl.kubernetes.io/last-applied-configuration` — именно сюда `kubectl apply` сохраняет копию твоего YAML-файла. Это нужно для того, чтобы `apply` мог вычислять разницу (diff) при следующем запуске.

## ⚖️ Аннотации vs Метки (Labels): В чем разница?

| Характеристика | **Метки (Labels)** | **Аннотации (Annotations)** |
| :--- | :--- | :--- |
| **Для чего** | Для поиска и идентификации | Для хранения метаинформации |
| **Использование в селекторах** | ✅ Да (можно фильтровать `kubectl get -l`) | ❌ Нет (по аннотациям нельзя фильтровать) |
| **Ограничения на размер** | Ограничены (короткие строки) | Практически не ограничены (могут быть большие JSON-блоки) |
| **Ограничения на формат** | Строгие (только буквы, цифры, дефисы) | Свободный (можно писать что угодно) |

## 📝 Пример в YAML

Вот как выглядит объект с аннотациями:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    app: my-app
    tier: backend
  annotations:
    # Для людей
    description: "Main API for payment processing"
    # Для инструментов
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
    # Для Helm
    meta.helm.sh/release-name: "payments-release"
```

## 💡 Важное правило для прода
**Никогда не используйте аннотации для логики самого приложения.** 
Приложение (например, Python-код) не умеет читать аннотации напрямую из своего пода. Аннотации — это удел **кластера** (Kubernetes API) и **вспомогательных инструментов** (Ingress, операторы, ArgoCD). Если приложению нужны данные, используй `ConfigMap` или переменные окружения.

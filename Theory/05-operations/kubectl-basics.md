# kubectl для начинающих: что это и как им пользоваться

Если ты только начинаешь изучать Kubernetes, начни с этой заметки. Здесь разберём, что такое `kubectl`, где он работает, как подключается к кластеру и как читать команды. Внутреннее устройство клиента и путь запросов подробно разобраны в [[how-kubectl-works]], а повседневные команды собраны в [[cheatsheet]].

## 1. Что такое kubectl простыми словами

**kubectl** (произносится примерно «куб-контрол») — это программа командной строки, с помощью которой инженер общается с Kubernetes.

Представь панель управления: ты вводишь команду, например «покажи Pods», а `kubectl` отправляет запрос в Kubernetes API и показывает ответ.

Важно:

- `kubectl` — не сам Kubernetes и не компонент, который запускает контейнеры.
- Обычно `kubectl` установлен на ноутбуке инженера или на машине CI/CD.
- Контейнеры запускают узлы кластера под управлением Kubernetes; `kubectl` только отправляет API-запросы.
- Для работы нужны сетевой доступ к API Server и учётные данные с достаточными правами.

Упрощённая схема:

```text
Твой компьютер
  |
  | команда kubectl
  v
kube-apiserver (входная точка Kubernetes API)
  |
  v
Контроллеры и другие компоненты Kubernetes
  |
  v
Pods на worker-нодах
```

## 2. Что нужно для подключения

### kubectl

Утилита должна быть установлена на компьютере. Проверить это можно командой:

```bash
kubectl version --client
```

Она показывает версию клиента. Эта команда не проверяет доступность кластера.

### kubeconfig

**kubeconfig** — файл настроек подключения. Обычно он находится в `~/.kube/config` (на Windows — в профиле пользователя, каталог `.kube\config`).

В нём могут храниться:

- адрес Kubernetes API Server;
- сведения о TLS-сертификате или доверенном центре сертификации;
- способ аутентификации: сертификат, токен или exec-плагин;
- описания кластеров, пользователей и contexts.

Не публикуй kubeconfig и не отправляй его в чаты: в нём могут быть действующие учётные данные.

Проверить, какой файл использует клиент, можно так:

```bash
kubectl config view --minify
```

Команда выводит настройки текущего context. Даже если токены скрываются, не публикуй полный вывод без проверки.

### Cluster, User и Context

- **Cluster** — описание подключения к конкретному Kubernetes API Server.
- **User** — способ аутентификации, который использует клиент. Это не обязательно локальная учётная запись компьютера.
- **Context** — комбинация cluster + user + необязательный namespace. Проще говоря, это выбранный набор настроек для работы.

Посмотреть contexts:

```bash
kubectl config get-contexts
```

Узнать текущий:

```bash
kubectl config current-context
```

Переключение context меняет целевой кластер и пользователя для последующих команд:

```bash
kubectl config use-context <context-name>
```

**Осторожно:** после переключения ты можешь случайно выполнять команды уже в другом кластере — например, production вместо тестового. Перед любой изменяющей командой проверяй context.

## 3. Как читать команду kubectl

Разберём пример:

```bash
kubectl get pods -n payments -o wide
```

| Часть | Что означает |
|---|---|
| `kubectl` | Запустить Kubernetes CLI |
| `get` | Прочитать список объектов |
| `pods` | Какой тип объектов показать |
| `-n payments` | Искать в namespace `payments` |
| `-o wide` | Показать дополнительные колонки, например IP и Node |

Другой пример:

```bash
kubectl describe pod payments-api-abc123 -n payments
```

Он просит Kubernetes показать подробную информацию об объекте Pod с указанным именем в namespace `payments`.

Общий шаблон:

```text
kubectl <действие> <тип-ресурса> [имя] [параметры]
```

## 4. Что такое ресурс, объект и namespace

**Ресурс (resource)** — тип сущности, с которой умеет работать Kubernetes API: например, Pod, Deployment, Service или ConfigMap.

**Объект (object)** — конкретный экземпляр ресурса, сохранённый в API. Например, Pod `payments-api-abc123` — объект типа Pod.

**Namespace** — логическая область имён внутри кластера. Он помогает разделять объекты разных приложений и команд. Например, Pod с именем `api` может существовать одновременно в namespace `payments` и `catalog`.

Если namespace не указан через `-n` / `--namespace`, kubectl использует namespace текущего context; если в context он не задан — обычно `default`.

Полезные команды:

```bash
kubectl get namespaces
kubectl get pods
kubectl get pods -n payments
kubectl get pods -A
```

Флаг `-A` (или `--all-namespaces`) показывает namespaced-объекты во всех namespace. Не каждый ресурс namespaced: например, Node и PersistentVolume относятся к уровню кластера.

## 5. Основные команды: сначала чтение, потом изменения

### Команды просмотра и диагностики

Эти команды запрашивают информацию и не меняют желаемое состояние объектов:

```bash
kubectl get pods -n payments
kubectl get deployments -n payments
kubectl describe pod <pod-name> -n payments
kubectl logs <pod-name> -n payments
kubectl get events -n payments --sort-by=.metadata.creationTimestamp
```

- `get` — краткий список или состояние объектов.
- `describe` — подробности об объекте и связанные Events.
- `logs` — вывод логов контейнера.
- `events` — события, которые помогают понять, что происходило при создании или работе объекта.

### Команды, которые меняют кластер

`apply`, `delete`, `scale`, `rollout undo` и некоторые другие команды изменяют состояние кластера. Не запускай их в незнакомом контексте.

- `apply -f file.yaml` — создать или обновить объект по YAML-манифесту.
- `delete` — удалить объект.
- `scale` — изменить количество реплик.
- `rollout undo` — откатить Deployment к предыдущей ревизии.

Перед применением существующего манифеста можно посмотреть предполагаемые изменения:

```bash
kubectl diff -f file.yaml
```

Серверная проверка без сохранения объекта (если API и admission webhooks поддерживают dry-run):

```bash
kubectl apply --dry-run=server -f file.yaml
```

Для этого учебного введения мы не используем `delete`, не меняем production и не применяем неизвестные манифесты.

## 6. Что такое YAML-манифест

**Манифест** — файл, в котором описано желаемое состояние Kubernetes-объекта. Например: «нужен Deployment с двумя репликами приложения».

Упрощённый пример:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hello
  namespace: default
spec:
  containers:
    - name: web
      image: nginx:1.27
```

Как читать основные поля:

- `apiVersion` — версия API, через которую описан объект.
- `kind` — тип объекта; здесь это Pod.
- `metadata` — имя, namespace, labels и другая информация об объекте.
- `spec` — желаемая конфигурация; здесь описан контейнер и его образ.

Манифест сам по себе ничего не запускает. Изменение попадёт в кластер только после отправки в API, например через `kubectl apply`.

## 7. Безопасный первый набор команд

Начни с команд, которые только читают состояние:

```bash
kubectl version --client
kubectl config current-context
kubectl get nodes
kubectl get namespaces
kubectl get pods -A
```

Если `kubectl get nodes` возвращает ошибку подключения — проверь VPN/сетевой доступ, адрес API Server и kubeconfig. Если возвращает `Forbidden` — подключение и аутентификация могли пройти успешно, но у пользователя недостаточно прав. Если `Unauthorized` — проблема обычно связана с аутентификацией или истёкшими учётными данными.

Не копируй токены, сертификаты и полный kubeconfig в тикеты или публичные чаты.

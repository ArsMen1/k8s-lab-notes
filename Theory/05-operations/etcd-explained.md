# etcd: хранилище состояния Kubernetes

`etcd` — распределённое consistent key-value хранилище. Kubernetes использует его как backing store для состояния API-объектов: Deployments, Services, Secrets, ConfigMaps и других ресурсов.

Важно: etcd не хранит содержимое PersistentVolume и данные внутри баз приложения. Он хранит Kubernetes API state и метаданные, необходимые control plane для управления кластером.

## Raft, leader и quorum

etcd использует алгоритм консенсуса Raft. В production обычно выбирают кластер из 3 или 5 членов: нечётное число удобно тем, что добавление четвёртого члена к трём не увеличивает число отказов, которые можно пережить.

1. Один член становится leader.
2. Запросы, требующие консенсуса (в частности, записи), обрабатываются через leader. Клиент может обратиться к любому члену: follower автоматически перенаправит такой запрос leader.
3. Изменение считается committed после подтверждения большинства членов.

Кворум для кластера из `n` членов: `floor(n / 2) + 1`.

| Членов etcd | Кворум | Допустимо потерять |
|---:|---:|---:|
| 1 | 1 | 0 |
| 3 | 2 | 1 |
| 5 | 3 | 2 |

Если потеряно большинство, etcd не может commit-ить новые записи и обслуживать операции, которым нужен quorum. Не рассчитывай, что API Server продолжит полноценно обслуживать все запросы: часть чтений может использовать watch cache, но изменения состояния и согласованные операции будут нарушены.

Уже запущенные контейнеры могут продолжать работать: kubelet на Node выполняет локальный жизненный цикл. Но контроллеры не смогут нормально получать и сохранять новое желаемое состояние, поэтому кластер нельзя считать здоровым.

## Как Kubernetes использует etcd

В etcd Kubernetes хранит API-объекты с ключами под registry prefix; типичный формат выглядит как `/registry/<resource>/<namespace>/<name>`. Это внутреннее представление, не API-контракт для ручной работы.

Когда выполняется `kubectl get`, запрос идёт в API Server. Для чтения API Server может использовать watch cache; не каждый запрос обязательно превращается в прямое чтение etcd. Изменения API Server валидирует, авторизует и сохраняет в backing store.

## Что делать при потере quorum

- Не перезапускай все члены etcd одновременно и не удаляй data directories.
- Определи, потеряны ли сами данные или только связь между членами; проверь topology, disk, network и состояние каждого member.
- Если данные сохранились, восстановление quorum/членов выполняют по процедуре etcd для конкретной topology.
- Если потеряны все пригодные копии данных, восстановление возможно из проверенного snapshot и требует отдельной процедуры.

Плановый backup обязателен. Snapshot нужно хранить вне узла/кластера, защищать доступом и регулярно проверять; наличие файла само по себе не доказывает, что restore сработает.

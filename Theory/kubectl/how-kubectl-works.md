# ⚙️ Архитектура и внутренняя работа kubectl

`kubectl` — это легковесный CLI-клиент (утилита командной строки), написанный на Go. Он не управляет контейнерами напрямую и не выполняет логику внутри кластера. Его единственная задача — транслировать команды пользователя в стандартные HTTPS-запросы к REST API Kubernetes и красиво форматировать ответы.

---

## 🏗️ Откуда и как запускается kubectl

Для работы `kubectl` не нужно находиться внутри кластера. Клиент полностью автономен и может быть запущен на любой машине при соблюдении двух условий:

1. **Сетевой доступ** к `kube-apiserver` (по умолчанию порт `6443`).
2. **Файл конфигурации (**`kubeconfig`**)** — обычно расположен по пути `~/.kube/config`. Он содержит адреса API-серверов, токены, ключи и сертификаты для аутентификации.

```
При наличии нескольких файлов конфигурации передать необходимый можно через--kubeconfig
kubectl get pods --kubeconfig=/path/to/my/special-config.yaml
```

### Топология запуска:

* **Локальный компьютер инженера / CI/CD ранер (Best Practice):** Основной сценарий в продакшене. Администратор или конвейер деплоя управляет кластером удаленно через защищенное сетевое соединение.
* **Мастер-нода (Control Plane):** Используется для низкоуровневой отладки самого кластера. Конфиг администратора обычно лежит в `/etc/kubernetes/admin.conf`.
* **Ворк-нода (Worker Node) ⛔ Не рекомендуется:** Запуск команд управления с рабочих узлов нарушает принципы безопасности (модель наименьших привилегий). В случае компрометации ворк-ноды злоумышленник не должен получить доступ к API всего кластера.

## 🔄 Глубокий разбор: `kubectl apply -f my-file.yaml`

Когда вы отправляете манифест в кластер, происходит строго последовательный процесс на стороне клиента и сервера:

```
[ kubectl (Клиент) ]  
│ 1. Чтение YAML -> Валидация -> Конвертация в JSON  
│ 2. Аутентификация по kubeconfig  
▼  
[ kube-apiserver (Мастер-нода) ]  
│ 3. Проверка прав (RBAC) + Валидация схемы ресурса  
│ 4. Вызов Mutating/Validating Webhooks (опционально)  
▼  
[ etcd (База данных) ]  
│ 5. Запись желаемого состояния (Desired State)
```

### 1. Этап клиента (`kubectl`)

1. **Чтение и парсинг:** Клиент считывает YAML-файл (`-f`).
2. **Синтаксический анализ:** Проверяет корректность структуры данных и переводит YAML в **JSON** (внутренний «язык» общения компонентов Kubernetes).
3. **Обнаружение API (API Discovery):** `kubectl` считывает поля `apiVersion` и `kind` (например, `apps/v1` и `Deployment`). Он кэширует схемы API кластера и проверяет, поддерживает ли текущий `kube-apiserver` данный тип ресурса.
4. **Транспортировка:** Клиент извлекает учетные данные из `kubeconfig`, формирует HTTP-запрос (обычно `POST`, `PUT` или `PATCH`) и отправляет JSON-нагрузку на эндпоинт API-сервера.

### 2. Этап сервера (`kube-apiserver`)

1. **Аутентификация и авторизация (RBAC):** Проверяет, кем является пользователь и разрешено ли ему выполнять операции над этим ресурсом в конкретном `namespace`.
2. **Admission Control:** Пропускает объект через цепочку плагинов безопасности (например, проверку лимитов) и вебхуков (Mutating/Validating Webhooks).
3. **Сохранение состояния:** API-сервер транслирует изменения в распределенное хранилище `etcd` (единственный источник правды в кластере).
4. **Асинхронное выполнение:** Как только запись в `etcd` подтверждена, API-сервер возвращает клиенту статус (`created`, `configured` или `unchanged`). Контроллеры Kubernetes (например, `Kube-Controller-Manager`) увидят новую запись в `etcd` и начнут приводить кластер к этому состоянию асинхронно.

> 💡 **Декларативный подход (Declarative):** Команда `apply` описывает *желаемое конечное состояние*. В отличие от императивных команд (создай, удали), `apply` высчитывает разницу (diff) между тем, что отправлено, и тем, что уже сохранено в `etcd`. Её можно запускать бесконечное число раз без риска сломать или дублировать инфраструктуру.

## 🔍 Глубокий разбор: `kubectl logs -l app=APP_LABEL`

Запрос логов демонстрирует распределенную природу Kubernetes, где мастер-нода выступает исключительно в роли диспетчера и прокси-сервера:

```markdown
[ Ваш Ноутбук ] ──(1. HTTP GET logs)──> [ kube-apiserver ]
│
(2. Поиск подов по лейблу в etcd)
(3. Проксирование запроса к нодам)
│
▼
[ Worker Node / Kubelet ]
│
(4. Чтение лог-файла с диска)
```

1. **Запрос:** `kubectl` отправляет HTTP-запрос на получение логов к `kube-apiserver`.
2. **Поиск:** API-сервер обращается к `etcd`, находит все поды с меткой `app=APP_LABEL` и определяет, на каких конкретно **Worker-нодах** они запущены.
3. **Делегирование:** API-сервер открывает защищенное соединение с демоном `kubelet` на целевых Worker-нодах.
4. **Сбор данных:** `kubelet` обращается к рантайму контейнеров (CRI, например, `containerd`), находит файлы логов на диске ноды (обычно в `/var/log/pods/...`) и передает их поток (stream) обратно в `kube-apiserver`.
5. **Вывод:** API-сервер перенаправляет этот поток в ваш терминал.

## 🌐 Сетевой путь трафика: Service -> EndpointSlice -> Pod

Когда клиент (внутри или снаружи кластера) отправляет запрос на IP-адрес Сервиса (`ClusterIP`), этот запрос проходит через абстрактные слои маршрутизации, прежде чем попасть в конкретный контейнер.

### 🖼️ Архитектурная схема прохождения трафика

```
[ Клиент (Трафик) ]  
│  
▼  
[ ClusterIP Service ] <─── ( Логическая группа / Постоянный IP и Порт )  
│  
├──► [ EndpointSlice ] ──► [ Список IP-адресов живых подов ]  
│  
▼  
[ kube-proxy ] <─── ( Читает EndpointSlice и обновляет правила IPTables / IPVS )  
│  
├─── Трансляция IP (DNAT) на уровне ядра Node  
▼  
┌────────────────────────────────────────────────────────┐  
│ Worker Node (Ядро Linux)                               │
│                                                        │
│ Маршрутизация пакета на IP конкретного пода...         │ 
└──────────────────────────┬─────────────────────────────┘  
│  
▼  
[ Target Pod ]  
│  
[ Container (api) ]

```

---

### ⚙️ Детальный пошаговый алгоритм (Под капотом)

#### 1. Создание ориентиров (Control Plane)

* Когда вы деплоите `Service`, ему выделяется виртуальный, неизменяемый IP-адрес из диапазона кластера (`ClusterIP`).
* Одновременно с этим встроенный `EndpointSlice-контроллер` ищет все работающие поды, которые подходят под селектор (`selector`) вашего сервиса.
* Контроллер создает объект `EndpointSlice`. Это масштабируемый реестр, где лежат сетевые адреса (`IP:Port`), готовность (`Ready/NotReady`) и топологические данные (зона, нода) всех целевых подов.

#### 2. Магия на ворк-нодах (`kube-proxy`)

* На каждой Worker-ноде запущен демон `kube-proxy`. Он постоянно слушает (подписан на события) `kube-apiserver`.
* Как только `EndpointSlice` создается или обновляется (например, под упал или добавился новый при масштабировании), `kube-proxy` на каждой ноде моментально считывает эти изменения.
* `kube-proxy` идет в ядро операционной системы ноды и обновляет низкоуровневые правила маршрутизации — чаще всего через `IPTables` или `IPVS`.

#### 3. Прохождение пакета (Data Plane)

1. **Запрос:** Пакет от клиента отправляется на IP-адрес `Service` (например, `10.96.0.10:80`).
2. **Перехват:** Как только пакет пытается покинуть ноду или проходит через сетевой стек ядра, срабатывают правила `IPTables / IPVS`, созданные `kube-proxy`.
3. **Балансировка (DNAT):** Ядро Linux прямо в памяти «на лету» подменяет IP-назначения (Destination NAT). Оно случайным образом (или по весам) выбирает один из IP-адресов подов, который `kube-proxy` взял из `EndpointSlice`. IP сервиса `10.96.0.10:80` превращается, например, в реальный IP пода `10.244.1.45:8080`.
4. **Доставка:** Пакет маршрутизируется внутри виртуальной сети кластера (CNI, например, Calico, Cilium, Flannel) и прилетает на сетевой интерфейс (`veth` пару) конкретного пода, попадая прямиком в ваше приложение.

---

### 🔌 Особый случай: Внешний трафик (снаружи кластера)

Схема выше идеально работает для **внутреннего** клиента (например, пода `frontend`, который стучится к поду `backend`). Но если запрос приходит **из интернета** (с вашего ноутбука), путь меняется. Пакет не может просто «возникнуть» внутри виртуальной сети кластера.

#### Как трафик попадает внутрь?

За это отвечают типы Сервисов `NodePort` и `LoadBalancer`, либо `Ingress` (который сам по себе использует `NodePort` или `LoadBalancer` под капотом).

**Путь для** `NodePort` **(например,** `30080`**):**

1. **Внешний клиент** отправляет запрос на публичный IP-адрес любой Worker-ноды (например, `192.168.1.100:30080`).
2. Пакет приходит на физический интерфейс сервера (на порт `30080`).
3. `kube-proxy` на этой ноде заранее настроил правило `IPTables`: *"Все пакеты, приходящие на порт* `30080`*, перенаправляй в* `ClusterIP` *сервиса"*.
4. **DNAT и доставка**: Дальше пакет проходит тот же путь, что и внутренний трафик: `IPTables` подменяет IP на конкретный под из `EndpointSlice`, и пакет улетает по внутренней сети (CNI) к нужному контейнеру.

   *Важно:* `kube-proxy` может перенаправить пакет на под, который находится на *другой* ноде (не на той, куда пришел запрос). В этом случае пакет будет прыгать между серверами внутри кластера.

**Путь для** `Ingress` **(L7):**

1. Внешний клиент стучится на IP балансировщика (или ноды).
2. Трафик попадает в **Ingress Controller** (например, Nginx, который запущен как обычный под внутри кластера).
3. Ingress Controller анализирует HTTP-заголовки (домен, путь) и сам проксирует запрос на внутренний `ClusterIP` нужного Сервиса.
4. Далее — стандартный путь через `EndpointSlice` к поду.

#### Главное отличие

* **Внутренний трафик** идет сразу на `ClusterIP` (виртуальный IP, который существует только в правилах `iptables`).
* **Внешний трафик** сначала должен «пробить броню» и попасть на реальный физический порт ноды (`NodePort`), и только потом `kube-proxy` переводит его на `ClusterIP`.

### 🧠 В чем разница между старыми `Endpoints` и новыми `EndpointSlice`?

| Критерий | Старый `Endpoints` | Новый `EndpointSlice` |
| :--- | :--- | :--- |
| **Структура** | Один огромный монолитный объект на один Service. | Разбивается на несколько небольших «кусочков» (по умолчанию до 100 подов в каждом). |
| **Проблема масштабирования** | Если в сервисе 5000 подов, то при изменении *одного* пода весь объект (весом в мегабайты) заново пересылался на *все* ноды кластера. Это вызывало перегрузку `kube-apiserver` и сети. | При изменении пода обновляется только один маленький Slice (остальные ноды не трогаются). Кластер тратит в сотни раз меньше трафика. |
| **Дополнительные фичи** | Только базовые IP и порты. | Поддержка гибридных сетей (IPv4 + IPv6), учет топологии (маршрутизация на поды в той же зоне для экономии денег). |

# Spring Cloud Config Server: Подробный разбор

## 🎯 Что это и зачем нужен?

Spring Cloud Config Server — это централизованный сервер конфигурации для микросервисов (обычно на Spring Boot). Он решает проблему «разбросанных» настроек: вместо того чтобы хранить пароли и адреса БД в 50 разных репозиториях, ты хранишь их в одном месте (обычно в Git), а приложения забирают их при старте.

**Паттерн работы:**

1. **Config Server** подключается к Git-репозиторию с конфигами (`.yml`, `.properties`).
2. **Микросервисы (Config Clients)** при запуске стучатся на Config Server: «Я сервис `payments-api`, окружение `prod`, дай мне мои настройки».
3. Config Server находит нужный файл (`payments-api-prod.yml`), отдаёт его по HTTP.

## 🏗️ Как это связано с Kubernetes?

В K8s есть свой механизм конфигурации — `ConfigMap` и `Secret`. Они работают на уровне **инфраструктуры** (прокидывают переменные окружения или файлы в под).

Spring Cloud Config Server работает на уровне **приложения**. В проде их часто комбинируют:

* Через K8s `ConfigMap` в под прокидывается **адрес Config Server'а** (переменная `SPRING_CLOUD_CONFIG_URI`).
* Сам Config Server разворачивается в K8s как обычный `Deployment`.
* Config Server уже раздаёт бизнес-настройки (пароли, фича-флаги) из **своего** Git.

## 🔐 Шифрование паролей (Главная фича)

Хранить пароли в Git в открытом виде — плохо. Config Server умеет шифровать значения. В Git лежит зашифрованная строка с префиксом `{cipher}`, а Config Server расшифровывает её перед тем, как отдать клиенту.

### Типы шифрования:

1. **Симметричное (проще)**: Один общий секретный ключ для шифрования и расшифровки.
2. **Асимметричное (RSA, безопаснее)**: Пара ключей (публичный шифрует, приватный расшифровывает).

### Как настроить (Симметричный ключ):

В `application.yml` самого Config Server'а (или через переменную окружения):

```yaml
encrypt:
  key: ${CONFIG_ENCRYPTION_KEY} # Секретная строка
```

Или в переменной окружения: `export CONFIG_ENCRYPTION_KEY=my-super-secret-key`

### Как зашифровать значение:

Отправь POST-запрос на эндпоинт Config Server'а:

```bash
curl -X POST http://localhost:8888/encrypt \
  -H "Content-Type: text/plain" \
  -d 'mySecretPassword'
```

В ответ придёт строка вида: `AQBvYml0bW9yZS5jb20...`

### Как использовать в конфиге:

В Git-файле (`payments-api-prod.yml`) пишешь:

```yaml
spring:
  datasource:
    password: '{cipher}AQBvYml0bW9yZS5jb20...'
```

Когда клиент запросит конфиг, Config Server увидит префикс `{cipher}`, расшифрует значение своим ключом и отдаст клиенту **уже расшифрованный** пароль.

## 🚨 Проблемы в Killercoda (и как их решить)

В Killercoda кластер **эфемерный** — он удаляется после завершения сессии. Это значит:

1. Твой Config Server (если ты его развернул) исчезнет.
2. При следующем заходе тебе придётся разворачивать его заново.

**Решение:** Храни манифесты для развертывания Config Server в своём Git-репозитории (как мы делаем с остальными манифестами). Тогда при новом заходе в Killercoda ты просто:

1. Клонируешь репо.
2. Применяешь манифест Config Server'а через `kubectl apply -f`.
3. Продолжаешь работу.

Это даже полезно: ты отработаешь навык «развернуть сервис с нуля», который пригодится в проде.
